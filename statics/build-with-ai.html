Docker, explained.

Docker gives every developer the same repeatable environment. Windows hosts Docker; the application and dependencies live inside containers.

The simple mental model

A container is an isolated workspace for one running service.

  • Image: packaged blueprint for a runtime, database, web server, or app.
  • Container: running instance of an image.
  • Dockerfile: instructions for building an image.
  • Compose file: map of connected services.
  • Docker Hub: registry where images are shared.

Daily commands

Compose reads compose.yaml, downloads missing images, mounts source code, and starts services.

docker compose upStart
docker compose logs -fWatch logs
docker compose exec app shShell in app
docker compose downStop

Connections and data

  • Ports connect containers to the browser.
  • Volumes share files or preserve data.
  • Environment variables hold configuration; keep secrets out of Git.

Why teams use it

  • Same runtime and dependency versions.
  • One documented startup command.
  • Testing matches delivery environments.
  • Databases need not be installed on Windows.

Dockerfile: build one image

Save this file as exactly Dockerfile. It is the recipe for your application image.

# Pick the required runtime
FROM <runtime-image>
WORKDIR /app
COPY <dependency-files> ./
RUN <install-dependencies>
COPY . .
EXPOSE <port>
CMD ["<start-command>"]
  • FROM selects a base image.
  • WORKDIR sets the folder inside the image.
  • COPY moves project files into it.
  • RUN performs build setup.
  • CMD starts the container.
docker build -t my-app .Build
docker run --rm my-appRun

Compose file: run the system

Save as compose.yaml. It describes app, database, cache, worker, and other services.

services:
  app:
    build: .
    ports:
      - "8080:8080"
    volumes:
      - .:/app
    environment:
      DATABASE_URL: <local-value>
    depends_on:
      - database
  database:
    image: <database-image>
volumes:
  database-data:
  • services lists containers.
  • build uses the local Dockerfile.
  • image downloads a ready-made image.
  • ports maps Windows to container ports.
  • volumes share or preserve data.
  • environment passes configuration.
docker compose up --buildBuild and start
docker compose downStop
Security rule

Never put passwords or API keys in Dockerfiles, Compose files, or Git. Use a local .env file and a proper secret store for shared or production environments.

Markdown files for people and AI.

Files ending in .md are plain-text documents that preserve project knowledge.

The front door of a project for people.

Repository instructions for AI coding agents that recognize this convention.

- Keep changes focused.

  • Architecture conventions

Ask before changing a schema.
Run tests after changes.

SKILL.md: reusable task playbook

A SKILL.md describes one repeatable AI task such as release preparation, UI review, or migration. Its exact location and loading behavior depend on the AI product.

# Release checklist
## When to use
Before creating a release.
## Steps
1. Read the changelog.
2. Run the full test command.
3. Build the Docker image.

How they work together

  • README: teaches people.
  • AGENTS: gives compatible agents repository rules.
  • CLAUDE: gives Claude project context.
  • SKILL: defines a reusable task.

These files do not replace tests, access control, review, or security tools. Check the AI product documentation to confirm support.

Good practice

Keep instructions short, specific, and testable. Put runnable commands beside expected results and update the files when the workflow changes.

Best Practice.

Speed is useful only when you can trust what you ship.

Never outsource judgment

  • Never paste passwords, API keys, or private customer data into AI.
  • Read generated code before running it.
  • Create Pull Request and do Peer Review
  • Check dependencies and licenses.

Your daily finish line

  • The app runs from a clean checkout.
  • Tests pass and changed behavior was checked.
  • Make sure to Commit once you test and certify the requirements.
  • Your commit explains what changed and why.
